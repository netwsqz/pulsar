# 规格：手机本地缓存（离线能听）

**Status:** 部分作废（2026-10-25）

> 仍然有效的部分：曲库快照（工单 02）、离线标灰判定、完整副本判据、`guardedIo` 兜底套路、

## 问题陈述

App 里的歌**一个字节都不在手机上**——每次播放都是现从 Jellyfin 拉流（`{服务器}/Videos/{id}/stream?static=true`，token 只走 header）。手机端目前除 DataStore 那个配置文件外，**零本地文件 I/O**，`AndroidManifest.xml` 里一个存储权限都没有。

具体疼在哪：

- **没网 = 一首也听不了**。电脑关机、Jellyfin 没起、出门在外连不上，App 打开就是一片空白——**连列表都是现拉的**，缓存过的歌你也找不到、点不着。
- 网络一抖就卡，起播要等整个缓冲。
- 同一首歌反复听，每次都要重新下载一遍，白花流量。

曲库在 `E:\file\Te_Music`（823 个文件 / 20.76 GB / 577 首 FLAC）。

## 解决方案

**听过的歌在手机上自动留一份副本**，没网时照样能放。

- 缓存**自动产生**：播放时顺手留下，没有「下载」按钮，用户不用管
- 缓存**可以自动扔**：上限 5 GB，超了自动淘汰最旧的（依据见 [ADR-0003](../../docs/adr/0003-cache-is-a-copy.md)）
- **存原文件**，不转码——副本跟曲库里那份一模一样
- 断网时 App **照常能用**：列表从曲库快照来，缓存的正常放、没缓存的标灰

## 名词

- **缓存 / Cache**、**曲库快照 / Library snapshot**——定义见 `CONTEXT.md`，别另造词
- **完整副本**：整首歌的字节都在手机上。**半截的**（听到一半切走）不算数——离线时按「没缓存」处理，但副本留着不删，下次在线听到它时自动补齐
- **标灰**：界面上表示「能看到、但现在放不了」。跟「没有这首歌」是两回事

## 铁律

**1. 缓存是增强，不是依赖。** 缓存层出**任何**问题——写不进去、索引库坏了、目录被删了、读缓存报错——都必须**退回直接走网络播放**，绝不因此播不了歌。缓存挂了顶多是没有离线能力，不能变成新的故障源。

**2. 缓存是副本，可以自动扔；「下载」不是。** 见 ADR-0003。缓存满了自动淘汰最旧的，不需要用户点头；将来若做「下载」，那些文件必须排除在自动淘汰之外。

**3. 缓存层绝不碰电脑上的曲库。** 删缓存、清缓存只动手机本地。网络失败、PC 服务没开，都不影响清缓存这件事成功。

**4. 快照只在线下兜底，不在线上抢活。** 能连上 Jellyfin 时一律以服务器返回为准；快照只在请求失败时顶上。它**不是加速缓存**——所以「在电脑上改了名手机不更新」这类问题不会出现。

**5. 退出登录才清缓存，会话过期不清。** 主动退出登录 = 清空（跟现有「换账号清空所有库缓存」的约定一致）；只是 token 过期不算——那是常事，一过期就清 5 GB 太亏。

**6. 不引入新权限。** 全程 App 私有目录，`AndroidManifest.xml` 一行不改。

## 用户故事

### 攒缓存

1. 作为使用者，我想听过一遍的歌自动存在手机上，下次没网也能听，不用我手动做什么。
2. 作为使用者，我想缓存占到 5 GB 时最旧的副本自动被淘汰，而不是让我自己去清理。
3. 作为使用者，我想被淘汰的是**最久没听的**，而不是我刚听过的那首。
4. 作为使用者，我想缓存存的是原文件，音质跟在线听一模一样。
5. 作为使用者，我想用蜂窝流量听歌时也照样留下副本——哪怕这会花我的流量。
6. 作为使用者，我想在电脑上把某首歌换成另一个版本时，手机上的旧副本继续能用（不做陈旧检测）——歌还是那首歌。

### 断网时

7. 作为使用者，我想断网打开 App 不是一片空白，而是照常看到我的专辑和全部音乐。
8. 作为使用者，我想一眼看出哪些歌能放、哪些不能（标灰），而不是点进去才发现放不了。
9. 作为使用者，我想只缓存了一半的歌被当作「不能放」，免得我点进去听一分钟就断掉。
10. 作为使用者，我想断网时还能搜索——在本地那份快照里搜，并且界面明确告诉我这是「离线搜索」，范围比在线小。
11. 作为使用者，我想断网时点播放列表，得到一个「需要联网」的明确说明，而不是转圈或者崩掉。
12. 作为使用者，我想断网时正在播的歌播到没数据就停下并告诉我，**不要自动乱跳下一首**。
13. 作为使用者，我想恢复联网后不用做任何操作，App 自己就回到在线状态。

### 看得见、清得掉

14. 作为使用者，我想在设置页看到缓存占了多少空间、存了多少首。
15. 作为使用者，我想能一键清空缓存，清之前有个确认框。
16. 作为使用者，我想知道清空缓存**不会**删掉电脑上的歌。

### 跟现有功能的关系

17. 作为使用者，我想在 App 里删掉一首歌时，手机上的副本也一起清掉——别占着我空间。
18. 作为使用者，我想**改名不影响缓存**——歌还是那首，照样能放，列表显示新名字。
19. 作为使用者，我想退出登录时缓存被清空（换账号不串数据）；只是登录过期不算，重登回来缓存还在。
20. 作为使用者，我想缓存的歌在 **USB 独占**下播放效果跟在线听完全一样——位深协商、静音跳曲、回放增益都不受影响。
21. 作为使用者，我想**回放增益在离线时也生效**（每首歌的响度修正量跟着快照一起存下来了）。

### 不出事

22. 作为使用者，我想缓存出任何问题都不影响我正常听歌——只是退回网上直接播。
23. 作为使用者，我想刚装好、还没有任何缓存时，App 一切照常（只是没有离线能力）。

## 实现决策

### 音频缓存走 Media3 官方方案，不自研

用 Media3 的 `SimpleCache` + `LeastRecentlyUsedCacheEvictor`（5 GB），在现有 `AuthHttpDataSourceFactory` 外面套一层 `CacheDataSource.Factory`，再交给 `DefaultMediaSourceFactory`。

**为什么**：`SimpleCache` 天然就是「命中读本地、未命中边读边写」，还自带 LRU 淘汰和索引。自研要处理并发写、seek、半截文件、淘汰记账——几百行高风险代码，正是本项目的重灾区（见 USB 那条链路的教训）。

**为什么要多两个依赖**：现在只声明了 `media3-exoplayer` / `media3-session` / `media3-ui`，`SimpleCache` 所在的 `media3-datasource` 只是传递依赖，索引数据库 `media3-database` 根本没进来。两个都要显式加上。

**代价**：磁盘上的缓存文件不是人类可读的目录结构。可以接受——按决策 6 它们本来就在 App 私有目录里，文件管理器看不见。**别为了"文件好看"去自研。**

**用 `FLAG_IGNORE_CACHE_ON_ERROR`**：读缓存出错就退回网络，直接对应铁律 1。

### 缓存目录用 filesDir，不用 cacheDir

`cacheDir` 会在手机空间紧张时被系统清掉，设置里的「清除缓存」也会把它整锅端——而这 5 GB 是专门为「出门能听」攒的，被系统随手清掉最伤。

### 曲库快照

一份 JSON 落在 App 私有目录，内容是曲库那几屏需要的专辑与曲目列表（歌名、专辑、时长、封面标识、**回放增益**）。在线请求成功时顺手覆写，请求失败时读它顶上。

**只覆盖这几屏**：发现 / 全部音乐 / 专辑（+ 离线搜索）。**播放列表不进快照**——离线时那一屏明说「需要联网」。

### 离线可播判定

只有**完整副本**标为可播。判据见下方「完整副本的判据」——已定，零成本。

### 缓存归属与清理

缓存按「服务器地址 + 用户 ID」打得清归属。主动退出登录 → 清空；token 过期 → 不清。删歌（走 ADR-0001 的 PC 伴生服务那条路）成功时，顺带删掉这首的本地副本。

### 接口与缝

两个新接口，都照项目已有的 `SessionRepository`（接口）/ `SessionStore`（实现）那套写，通过 `JellyfinViewModelFactory` 注入：

- **`MediaCache`** —— 手机本地音频副本。回答「这首歌有完整副本吗」、报「占了多少 / 多少首」、执行「清空」和「删掉某首」。生产实现包 `SimpleCache`。
- **`LibrarySnapshotRepository`** —— 曲库快照的读写。生产实现落文件。

### 设置页

照 `RecycleBinSection` 的样子加一个独立的缓存区块（占用 + 清空 + 二次确认）。`CONTEXT.md` 里那套「占了用户空间就得让他看得见」（ADR-0002 定的）在这里复用。

### 不动的东西

**Jellyfin 数据层一行不改**（除非「待实测」的第 3 条被逼到）。播放服务、USB 独占链路、回放增益、静音跳曲**全部不动**——它们工作在音频输出那一层，跟数据是从网上来还是从手机里来无关。

## 测试决策

**缝**（按优先级，缝越少越好）：

1. **`MediaCache`（接口）** —— 本功能唯一的外部状态，且 `SimpleCache` 需要 Android Context 和真实数据库，JVM 单元测试里造不出来。用 `FakeMediaCache` 测 ViewModel。
2. **`LibrarySnapshotRepository`（接口）** —— ViewModel 测试用内存 Fake；文件实现自己用临时目录测（项目里已有 `File.createTempFile` 的先例）。

**测什么**：

- **纯函数**：快照的序列化/反序列化、离线搜索的过滤、缓存占用的人类可读格式化
- **`JellyfinViewModel`**（用现有 `FakeJellyfinApi` / `FakeSessionRepository` + 新的两个 Fake）：在线请求失败 → 读快照顶上；在线成功 → 以服务器为准并覆写快照；退出登录 → `clearCache()` 被调用；会话过期 → **没有**被调用；删歌成功 → 那首的副本被删；离线时 `streamUrl` 对没缓存的歌返回「不可播」而不是坏 URL
- **不测**：`SimpleCache` 自己的行为（那是 Media3 的事）、真实网络

**测试命名照项目惯例用反引号描述行为。** 注意：涉及轮询/长协程的场景要用有界 `advanceTimeBy`，别用 `advanceUntilIdle`（见 `QQDownloadViewModelTest` 的教训）。

## 明确不做

- **不做手动下载**（挑歌挑专辑点了才下）——那是「下载」，不是「缓存」
- **不做预取**（点开一张专辑就整张下下来）——会额外吃流量和电，而且它本质是换了个壳的「下载」
- **不做转码缓存**。用 320 kbps 能把 5 GB 塞进 1000+ 首，但这个项目的立身之本就是 USB 独占 + bit-perfect，为了多装几首把音频压成有损等于前面全白干。**嫌少就调大上限数字，别动音质。**
- **不做陈旧检测**（文件在服务器上被换过 → 不重下）。代价是旧副本会一直用到被淘汰为止；换来的是一条自愈路径：常听的歌被淘汰后会重下成新的。
- **不做单独的「离线歌」列表页**——界面跟在线时一样
- **不做缓存文件导出**（拷到电脑 / 别的播放器）
- **不做精细淘汰控制**（比如「这张专辑永久保留」）
- **不加蜂窝/ Wi-Fi 开关**——两种网下都缓存
- **不做缓存预热**（App 启动时后台扫一遍补齐）
- **不催 Jellyfin 刷新**、**不动 PC 伴生服务**

## 「完整副本」的判据（已定）

**用 Media3 自带的长度元数据，零成本。** 已反查 media3 1.5.1 的 dex 确认 API 存在：

```java
ContentMetadata meta = cache.getContentMetadata(key);
long total = ContentMetadata.getContentLength(meta);   // "exo_len"；-1 表示未知
boolean complete = total != C.LENGTH_UNSET && cache.isCached(key, 0, total);
```

`CacheDataSource` 在打开上游、拿到 HTTP 响应的 `Content-Length` 之后，会把它写进这条缓存的元数据（键是 `exo_len`）。

三条要注意的：

- **从没播过的条目 `getContentLength` 返回 -1**（元数据是空的）。但那种条目本来也没有副本、本来就算「没缓存」，不影响判定。
- **上游不给 `Content-Length` 时也是 -1**（比如转码 / chunked 流）。本项目的播放 URL 是 `?static=true`（直传原文件），**预期一定有**——但这是**预期**，实现时要在真机上对一次。**对不上的兜底口径：一律当作「不完整」**（宁可标灰，也不能让人点进去听一半断掉）。
- **别指望 `CacheUtil` 之类的辅助类**——1.5.1 的 dex 里没有它，直接用 `Cache` 接口的方法（`getContentMetadata` / `isCached` / `getCachedBytes`）。

**因此 Jellyfin 数据层不用动**，`Fields=MediaSources` 那条路作废（当初留它只是为了兜底）。

## 进一步说明

- 5 GB 上限管的是「手机存多少」，**不是「用掉多少流量」**——被淘汰的老歌再听会重新拉一遍。所以流量消耗上限是「你听了多少」，不是 5 GB。真要收口，以后再加开关
- 缓存能吃满的空间是按 FLAC 平均 36 MB/首算的：**5 GB ≈ 140 首**
- 手机端目前**零文件 I/O 代码**，这是本项目第一次在手机上落盘（DataStore 之外）。第一个动手的工单要把这个前提记在心里——没有现成模式可抄
