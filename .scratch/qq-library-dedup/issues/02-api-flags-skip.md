# 02 — 服务端：接口带标记 + 默认跳过

**What to build:** 搜索与专辑曲目接口回传的每首歌都带上「已在库」「下载中」两个标记；下载接口默认挡住已在库的，只有明确要求时才照下。做完用 curl 就能看到标记，并验证下一首已有的歌会被跳过。App 端一行都还没改。

**Blocked by:** 01 — 服务端：曲库索引与判定规则

**Status:** done

- [x] `/api/search` 回传的每首歌新增 `in_library`、`downloading` 两个布尔字段
- [x] `/api/album/{album_mid}/songs` 回传的每首曲目同样新增这两个字段
- [x] 「下载中」= 服务端任务队列里状态为 `queued` 或 `running` 的 song_mid
- [x] `/api/download`（单曲）请求体新增 `force`（默认 false）
- [x] 单曲已在库且未带 `force` 时**不入队**，回传一个可与正常入队区分的响应
- [x] 该「已跳过」响应的**字段形状必须与正常响应一致**（`job_id` 字段仍在，可为空串），并新增 `skipped` 字段供新客户端识别——否则旧版 App 会把它解析成「下载服务返回了无法识别的数据」
- [x] `/api/download/album`（整张）请求体同样新增 `force`
- [x] 整张下载默认跳过已在库的曲目，回传里**同时给出入队数（`count`）与跳过数（`skipped_count`）**
- [x] **显式传了 `song_mids` 时按用户勾选原样入队，不自动跳过**——勾选本身就是强制（见规格「实现决策」）
- [x] `/api/health` 新增索引状态：是否就绪 / 是否扫描中、索引到多少首
- [x] 索引未就绪时所有接口一律按「库里没有」处理，不报错、不阻塞请求
- [x] 老客户端不传 `force` 时不会报错（**但行为有变**：见 Comments 第 2 条，老客户端根本不带 `artist`，判定不出来 ⇒ 不拦）
- [x] 路由层单元测试：patch 掉索引，断言搜索 / 专辑曲目接口的标记正确；patch 掉入队函数，断言已在库时不入队、带 `force` 时入队、整张下载时跳过数与入队数正确、显式 `song_mids` 时不被跳过

## Comments

### 落地时超出工单的三处

1. **`artist` 进了请求体**（工单只写了 `force`）。判定要「歌名 + 歌手」，客户端不给歌手就没法判。App 端补上这个字段是工单 03 的事。
2. **「缺歌手就不敢判」的门槛**——见规格「实现决策」。审查用真库跑出铁证：库里 `鬼` 有两首不同歌手的、`Sorry` 也是；而现有 App 的请求体里没有 `artist`，只按歌名判会把「同名不同人」静默拦掉、且没有强下的口子。这是铁律禁止的那类误判，所以定成：**歌名和歌手都在才敢下结论**。代价是老客户端的单曲请求不被拦（回到今天的行为），App 补上 `artist` 后自动生效。
3. **专辑曲目接口多回一个 `singer`**（老客户端靠 `ignoreUnknownKeys` 忽略）。真接口确实带这个字段——已用叶惠美实测，11 首全部返回 `'周杰伦'`。原始需求是自造的 `qmc2.get_album_songs` 不带它，但同一底层接口的 `songInfo` 里有。

### 代码审查揪出的两个真问题（都已修，都有回归测试）

1. **重扫会把刚下完的歌清扫掉**（`library_index.py`）：重扫的目录快照是读标签**之前**取的，收尾时按旧快照清扫 ⇒ 这期间 `note_downloaded` 并进来的歌被当成「文件已删除」删掉，最长 3 分钟内又变回「库里没有」，整张下载会把它再下一遍——正是本功能要消灭的重复。改成按「文件现在还存不存在」判，而不是「在不在快照里」。
2. **单曲跳过只看歌名** —— 就是上面第 2 条门槛的由来。

### 真服务实测（2026-09-16）

- `/api/health` → `library: {root, ready: true, count: 596}`
- 搜索「晴天」：`晴天/周杰伦` → 已在库 ✓；`晴天 (Live)/周杰伦` → 没有 ✓（括号保版本）
- 单曲（带歌名+歌手，已在库）→ `{"job_id": "", "skipped": true}`，未入队 ✓
- 整张叶惠美（11 首全在库）→ `{"count": 0, "skipped_count": 11}`，一首没下 ✓
- 服务端测试 98 个全过（原有 21 + 工单 01 的 46 + 本次 31）

### 已知未修（影响极小）

- 跳过判定跑在 `_enqueue` 的入参校验之前：非法 `song_mid`/`quality` 且歌名命中的请求会回 200 `skipped` 而不是 400。两种情况的净效果都是「没入队」，且客户端不会发出非法 mid（都来自搜索结果），故不改。
