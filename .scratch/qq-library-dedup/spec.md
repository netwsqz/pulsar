# 规格：QQ 下载「曲库去重」

**Status:** ready-for-agent

## 问题陈述

从 App 的 QQ 下载区块搜歌、选专辑下载时，用户看不出电脑的曲库里**已经有哪些歌**。

后果：

- 同一首歌被反复下载。每次重复下载都要走一遍「拿下载链接 → 下载 → 解密 → ffmpeg 转码 → 打标签 → 落盘」，白耗时间与带宽。
- QQ 侧接口调用次数成倍增加。服务端已经在用「单线程串行 + 每首 sleep 1 秒」防风控，重复下载等于白白消耗这份安全余量。
- 曲库里出现重复文件。侦察证实 `E:\file\Te_Music` 现有 16 组重复（同曲不同格式、同曲散落在两张专辑、下载器落一份 + 手动拷一份）。
- 用户点「整张下载」时无法知道这张专辑其实只缺一两首。

## 解决方案

电脑端服务维持一份**曲库索引**（后台定时扫描 Jellyfin 音乐库目录），在「搜索歌曲」「专辑曲目」两个接口里给每首歌带上 `in_library`（已在库）与 `downloading`（下载中）两个标记；下载接口默认跳过已在库的曲目，只有请求显式带 `force` 标志时才照下。

App 端把这些标记显示出来：搜索结果行与选曲弹窗里，已在库的曲目置灰并带标签，但仍可强制下载；「全选」只选未下载的；选曲弹窗顶部给出「共 N 首 · 已有 M 首」汇总。

**贯穿全局的一条铁律：判定不出来时一律按「没有」处理。** 索引未就绪、扫描失败、服务不可达、标签与文件名都读不出歌名——一律当成「库里没有」。这个功能是贴心助手，绝不能变成拦路虎。

## 实现决策

### 电脑端服务（`server/qqmusic_service.py`）

**索引范围**

- 只认 Jellyfin 音乐库目录 `E:\file\Te_Music`。
- `E:\music\library` 那 67 首**不算数**——那些歌不在 Jellyfin 库里，App 里根本搜不到、听不着。判成「没有」让用户重下一次反而是好事，正好把它们挪进真正的曲库。
- 只读。绝不写入、移动、删除曲库里的任何文件。扫描按扩展名过滤，跳过 `.nfo` 等非音频文件。

**判定钥匙**

- **优先读音频标签**（mutagen，服务环境已装 1.47.0），取 `TITLE` / `ARTIST` / `ALBUMARTIST`。
- 标签缺失或读不出歌名时，**回退解析文件名**（去掉开头的 track 号 / disc 号前缀、去掉 `_hires` `_H` 这类音质后缀、去掉扩展名）。
- 侦察已证实当前 595 个文件 100% 有完整标签，回退路径是为将来从外部拷进来的无标签文件准备的。

**比对规则**

- 先归一化：统一大小写、全角半角、省略号与引号问号等等价标点、压缩连续空格。
- **括号及其内容一律保留，绝不丢弃。** 括号里的 Live / Remix / Instrumental / 翻译恰恰是区分版本的关键；丢掉会让《晴天》和《晴天 (Live)》变成同一首。
- 歌名归一化后必须**完全相等**。
- 歌手归一化后须**一边包含另一边**（`Lady Gaga/Bruno Mars` 含 `Lady Gaga` ⇒ 算对上）。处理多歌手串联用 `/` 或 `&` 的写法差异。
- 缺少歌手信息时只按歌名判。
- **不判音质。** 已有的 128k 也算「已有」；想升级音质走「仍要下载」的口子。

**索引刷新**

- 后台线程按 **3 分钟**周期对比目录快照（路径集合 + mtime + size），**有变化才重扫**；无变化时请求直接读内存里的索引。
- 不做磁盘缓存。冷扫 595 个文件约 17 秒，热缓存约 0.5 秒；重启服务时系统页缓存通常还是热的。将来真觉得慢了再加。
- **索引未就绪时**（服务刚启动那十几秒）所有查询返回「未知」，路由层一律按「库里没有」处理，照常服务请求。绝不让用户干等。
- 服务端自己下载成功一首歌后，**立即**把它并入索引，不等下一次周期扫描。
- 但重扫的目录快照是**读标签之前**取的，这段时间里被 `note_downloaded` 并进来的歌不能当成「文件已被删除」清掉——判据不是「在不在快照里」，而是「文件现在还存不存在」。

**接口变更**

- 搜索歌曲接口：每首歌新增 `in_library`、`downloading` 两个布尔字段。
- 专辑曲目接口：同样新增这两个字段。
- 下载单曲接口：请求体新增 `force`（默认 false），并新增 `artist`（判定用；老客户端不传）。已在库且未带 `force` 时**不入队**，返回一个可与正常入队区分的响应，让 App 知道是「已存在被跳过」而非出错。
- **只有歌名和歌手都在，才敢判「已在库」。** 缺歌手时只按歌名判是在猜——真库里 `鬼`、`Sorry` 都各有两首不同歌手的，猜出来的必须一律当「没有」，与总铁律一致。这条同时管住三处：搜索与专辑曲目的标记、单曲下载、整张下载。**后果**：老客户端（请求体没有 `artist`）的单曲请求不会被拦（宁可让它重复下一次，也不能出现「我想下，它不让」）；App 端补上 `artist` 后，服务端这层保护自动生效。
- 下载整张接口：请求体同样新增 `force`。默认跳过已在库的曲目，回传里**同时给出入队数与跳过数**。
- **「跳过」只在「整张」时自动生效。** 请求显式带了 `song_mids` 时，服务端按用户勾选原样入队，不自动跳过——用户已经一首首挑过了，那是明确意图。这条是选曲弹窗「已在库的能勾、勾了照下」的落地方式：勾选本身就是强制。`force` 用于整张下载时强制全下。
- 健康接口：新增索引状态字段（是否就绪/扫描中、索引到多少首）。

**「下载中」的判定**

- 服务端任务队列里状态为 `queued` 或 `running` 的 song_mid。

### App 端

**数据层**

- `QQSongDto` / `QQAlbumSongDto` 增加 `inLibrary`、`downloading` 字段，带默认值。
- 客户端 JSON 解析已开启 `ignoreUnknownKeys`，服务端加字段不会导致老版本 App 崩溃——无需为兼容性做额外设计。

**状态层**

- `QQDownloadUiState` 新增一个全局 `Set<String>`（键为 song_mid）表示「已在库」。
  - **不**把标记塞进服务端 DTO——那是 data 层对象，在它上面挂 UI 专用字段是分层污染，且搜索结果是整批替换的，挂在单曲对象上的标记每搜一次就会丢。
  - 用 song_mid 作键是因为它是 QQ 侧稳定 id；而匹配本身只能靠歌名+歌手（服务端已完成），键必须落回 QQ 自己的 id。
- 「下载中」集合 = 服务端回传的 `downloading` 标记 ∪ 本地任务队列里 `queued`/`running` 的 song_mid。并集兼顾两者：服务端保证重启 App 后仍准，本地队列保证刚点下去还没轮询到时也立刻准。
- 任务轮询看到某个 mid 变为完成态时，**立刻**把它并入本地「已在库」集合（零额外请求、零延迟）。

**界面**

- **搜索结果行**：`in_library` ⇒ 下载图标禁用 + 一个「已在库」小灰标签，**歌名与歌手保持正常颜色**（中文歌名本来就难认，整行调暗会让人找不着歌）。`downloading` ⇒ 标「下载中」且不可点。
- **点已禁用的下载图标**：弹出确认「该曲已在库，仍要重新下载？」，确认则带 `force` 重发。
- **选曲弹窗顶部**：一行汇总「共 12 首 · 已有 8 首」。
- **选曲弹窗曲目行**：`in_library` ⇒ 带「已在库」标签、**能勾但默认不勾**，勾了照下；`downloading` ⇒ 带「下载中」标签、不可勾。
- **「全选」按钮**：改名「全选未下载」，只勾未在库的。
- **健康卡片**：新增一行「曲库：<目录> · N 首」。这一行的价值在于排查——它说某首歌没有、但用户明明有，用户能一眼分辨是「它看错目录了」还是「真的没有」。
- **专辑行**：**什么都不加**（理由见下）。
- **服务不可达 / 索引未就绪**：所有歌一律按「没有」处理，正常可点可勾。

### 明确不做的事

- **不做专辑行的「整张均已在库」标记。** 原计划靠文件夹名认专辑（便宜），但侦察推翻了：22 个专辑的文件夹名与标签里的专辑名对不上（标点被清洗、专辑名含 `/` 被拆成两层目录、单曲目录带「(单曲)」后缀），库里还有 10 处「歌手套歌手」的多层目录、最深 6 层，且有歌散落在别的专辑目录。认错的代价正是「明明没有却说有」。要认准就得为每张搜出来的专辑多调一次 QQ 接口（搜一次 10 张专辑 = 10 次额外请求，有风控风险）。而弹窗顶部的汇总行给出的答案不但免费而且准——用一行可能说错的字换一次点击，不值。
- **不做服务端持久化的 mid → 文件路径台账。** 下载器下完只把路径 print 一行，不持久化任何东西；文件名里没有 mid，音频标签里也没有 mid。账本只能从今天开始记，对库里现存的 595 首一本都查不到——功能等于白做，得等每首重下一遍才慢慢生效。将来可以锦上添花。
- 不做音质参与判定。
- 不做单独的「曲库浏览」界面（曲库内容 Jellyfin 那边本来就能翻、能搜、能听）。

## 测试决策

**好的测试长什么样**：只测外部行为——接口返回了什么、状态流变成了什么、哪些文件被读写了。不测实现细节（不测私有函数被调用了几次、不测内部数据结构的形状）。

### 服务端（`server/test_qqmusic_service.py`，扩展）

沿用现有先例：`unittest` + `unittest.mock.patch.object`，直接调用路由函数、patch 掉协作者。

- **纯函数直接测**：歌名/歌手归一化、同名判定、歌手「一边包含另一边」、括号保留、全角半角、无标签回退文件名。这些是风险最集中的地方，必须覆盖。
- **扫描器拆两半**：把「(文件名, 标签字典) → 身份」做成纯函数单元测试；「遍历目录 + 调 mutagen 读标签」的 IO 那半不做单元测试，靠真曲库验证命令覆盖。这样测试不需要在临时目录里造真的音频文件。
- **路由层测标记管道**：patch 掉索引，断言搜索/专辑曲目接口回传的 `in_library` / `downloading` 正确。
- **幂等与 force**：patch 掉入队函数，断言已在库时不入队、带 force 时入队、整张下载时跳过数与入队数正确。

### App 端

- **`QQDownloadViewModelTest`，扩展**：沿用现有的手写 `FakeQQDownloadApi`（先例就是它）。覆盖已在库集合的维护、任务完成后立刻标记、下载中的并集推导、force 重发的确认流程、服务不可达时全部按可点处理。
- **`QQDownloadDataSourceTest`，扩展**：Ktor `MockEngine`，覆盖新字段的 JSON 解析，以及服务端返回缺字段时仍能解析（向后兼容）。
- **界面层不做自动化测试**：项目没有 Compose UI 测试基建，也没有 `androidTest` 目录。界面由用户在自己手机上**亲眼看**验证——这是本项目一贯的做法。

### 验证命令（第一个工单的交付物）

服务端索引做完后，给用户一条命令，拿**真曲库**跑一遍，把「服务端认为已有哪些歌」列出来给用户亲眼过一遍。判定靠谱了再动 App 界面。

## 不在范围内

- 专辑行的「整张均已在库」标记
- 服务端持久化的 mid → 路径下载台账

## 补充说明

### 侦察结论（2026-09-14 实测，供实现参考）

**曲库 `E:\file\Te_Music`**（已证实就是 Jellyfin 音乐库：`E:\Data\root\default\音乐\Te_Music.mblink` 指向它，`EnableRealtimeMonitor=true`）：

- 结构 `歌手 / 专辑 / 文件` 三层，89 个歌手目录、245 个目录、820 个文件。
- 音频文件 595 个：`.flac` 575、`.ogg` 19、`.mp3` 1。其余 225 个是 Jellyfin 生成的 `.nfo`，扫库必须按扩展名过滤。
- 文件名两种风格并存：352 个下载器产出的 `NN 歌名.ext`；244 个外来风格 `歌手 - 歌名_hires.ext`。
- 下载器会清洗文件名：`<>:"/\|?*` 和控制字符替换为 `_`。`Mrs. GREEN APPLE` → `Mrs_ GREEN APPLE`，`Luv(sic) (12" Remix)` → `Luv(sic) (12_ Remix)`。**换不回来**——这是必须靠标签的原因。
- **595 个文件 100% 有完整标签**，包括那 244 个外来风格文件；标签里存的是**未清洗的原文**（`For Free?` 的问号、`Mrs. GREEN APPLE` 的点都在）。
- 陷阱：MP3 必须用 `mutagen.File(path, easy=True)` 才能取到标签（ID3 帧名是 `TIT2/TPE1`），否则返回 None。全库只有 1 个 mp3，但别踩。
- 16 组重复：含 Adele `Someone Like You` 的 flac+mp3 双份、Vaundy 同一专辑目录下 `02 灯火.flac` 与 `Vaundy - 灯火.flac` 并存、藤井风与 YELLOW黄宣 的歌跨专辑重复。
- 多碟：16 个文件带 `D-NN` 前缀，全是 disc 2，涉及 3 张专辑（`Stevie Wonder/Songs In The Key Of Life`、`林俊杰/她说 概念自选辑`、`陶喆/太平盛世`）。库里没有任何 `1-xx` 前缀。
- 22 个专辑的目录名与标签 ALBUM 值对不上；10 处多层歌手目录（最深 6 层：`Before You Exit/Connor McDonough/Luke Moellman/Riley McDonough/Toby McDonough/Jon Sandler/Silence/`）。
- 歌手写法脏：`Mrs. GREEN APPLE`、`I Don't Like Mondays.`（带尾点）、`Lady Gaga/Bruno Mars`、`BoA/三浦大知`。

**性能**（实测）：

| 手段 | 595 个文件 |
|---|---|
| mutagen 冷读 | ≈17 秒（28 ms/文件） |
| mutagen 热读 | ≈0.5 秒（0.2 ms/文件） |
| ffprobe | ≈19 秒（32 ms/文件，进程启动为主） |

结论：现扫不可行，必须「后台周期扫 + 内存索引」。
