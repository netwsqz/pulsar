# ADR-0002：删除 = 移到回收站，不真删

**状态：** 已接受（2026-09-18）

## 背景

App 里的「删除」是该真删文件，还是留条后路？

用户定过一条规矩：**不删用户数据**。而这是手机上的操作，手滑的成本极高——列表里点错一行，一首歌就没了，而且**不可逆**。

## 决定

**「删除」= 把文件移到 `E:\file\Te_Music_deleted`，保持原相对路径。**

界面上仍然叫「删除」，不叫「移到回收站」——用户不需要知道实现。App 设置页能看到回收站里有什么、能恢复、能手动清空。

**不自动清理。** 没有「30 天后自动真删」这种定时炸弹。

## 理由

- 一个在手机上删错、还得开电脑才能救回来的功能，跟不能救差别不大——所以**恢复按钮必须做**，否则回收站只多占一份磁盘空间
- 自动清理 = 定时删用户数据，与「不删用户数据」的规矩冲突。宁可让用户自己想起来去清
- 保持原相对路径，是为了让「恢复」变成一次纯挪动，不需要额外记账（不用维护一张「它原来在哪」的表）

**位置硬约束**：回收站**必须**在曲库目录外面。放 `E:\file\Te_Music` 里面会被 Jellyfin 当曲库扫进去，"删掉"的歌会原样出现在 App 里。

**不丢 Windows 回收站**（`$Recycle.Bin`）：那是系统内部格式，往里塞文件容易被系统清理策略搞掉。

## 后果

- 「删除」**不立刻释放磁盘空间**。设置页要显示回收站占用，让用户看得见
- 多一个目录要管，多三个接口（列出 / 恢复 / 清空）
- 删空专辑的最后一首歌时，剩下的 `album.nfo` 和空文件夹也一并挪进回收站（保持可恢复），否则 Jellyfin 里会留一个点进去没歌的空专辑
