# ADR-0007：下载取代自动缓存——手机上的副本一律由用户主动触发

**状态：** 已接受（2026-10-25）

**部分取代：** [ADR-0003](0003-cache-is-a-copy.md)（缓存自动淘汰的那部分作废；「副本删掉不丢数据」这条仍然成立）

## 背景

手机本地缓存（`.scratch/library-cache/`，工单 01-06）此前是**自动**的：听过一首歌就顺手留一份副本，攒到 5 GB 按最久没听淘汰。规格里当时明确写了「不做手动下载」「不做预取」。

用下来发现这套设计的意图和行为对不上：

- **用户攒了一堆没打算留的歌**，也不知道是哪来的（听一遍就留了）
- **想离线听某张专辑时反而要先联网听一遍** —— 需求是「提前存」，能力却只给「事后留」
- 5 GB LRU 会在用户不知情的时候把歌删掉，而删掉的是「最近没听的」——恰恰可能是他留着备用的

翻过来做更简单也更诚实：**用户点一下才存，存了就不会自己消失**。

## 决定

**1. App 不再自动存任何音频。播放链路纯只读。**

`CacheDataSource.Factory` 用 `setCacheWriteDataSinkFactory(null)` 进只读模式（bytecode 确认：`cacheIsReadOnly` 为 true 时 write data source 置 null，`openNextSource` 只在上游打开时才考虑写）。命中读本地、未命中直接走网络，一个字节都不写盘。

写盘只剩一条路：`CacheWriter`（media3 自带）+ `createDataSourceForDownloading()`。

**2. 用户主动「下载」，删掉自动淘汰。**

- 入口：**专辑详情页**、**播放列表详情页**各一个「下载」按钮
- 淘汰器从 `LeastRecentlyUsedCacheEvictor(5 GB)` 换成 `NoOpCacheEvictor` —— **什么都不自动删**
- **不设总量上限**，空间不够时由系统存储报警兜底

**3. 下载按「批次名单」记账，删除只删当初那批。**

下载时把「专辑/列表 id → 曲目 id 列表」写进 DataStore（`DownloadLedger`）。删除时按名单删，服务器后来新增的歌不在名单里、不受影响。已下载的专辑**不提示新增**，要补就删了重下。

**4. 「已下载」的判定永远是字节真相，不是名单真相。**

名单里存了不算数——只有 `ContentMetadata.getContentLength() > 0 && isCached(key, 0, total)` 成立才算「已下载」。App 被杀掉重进时，下了一半的专辑显示为「未下载」，再点一次只补缺的部分。

**5. 退出登录、切换账号都不清下载；按账号隔离可见性。**

- 名单按「服务器地址 + 用户 ID」归属，别的账号看不到
- 但**音频字节共享**（缓存键是播放 URL，不带用户 ID）：A 删了同一首歌的下载，B 的也没了，下次播放重下
- 主动退出登录**不清**下载（这是本次决定里最反直觉的一条，见下）

**6. 存量副本不做迁移——升级时直接清掉。**

原计划是「扫一次，把已有完整副本反推成下载名单」。**已撤销**：真机跑出来一批 `serverUrl`
为空的坏条目（离线启动走 `goOnline()` 时 `_state.value.serverUrl` 还是空串，写进去的归属全丢），
`entriesFor(真实地址, userId)` 一条都匹配不上，界面上明明有几个 G 却显示空的。

用户决定不修：老副本手动清掉，下载从零开始。迁移代码已整体删除。

## 理由

**为什么「下载」必须不可自动删。** ADR-0003 早就把「缓存」和「下载」分开定义了，代价写得很清楚：下载是用户主动要的、不能被自动清理。既然现在由用户主动触发，它就该归到「下载」那一栏。保留自动淘汰会让「我点了下载，一周后发现没了」变成一个必须解释的 bug。

**为什么退出登录也不清。** 跟「换账号清空库缓存」的既有约定冲突，但那条约定的目的是**防跨账号数据串扰**（曲库清单、播放队列串了会真的显示错东西）。音频字节不串：它就是一个文件，放出来是 A 的歌还是 A 的歌，不会变成 B 的。为了一个抽象的卫生规则删掉用户几十 GB 的主动下载，代价远大于收益。可见性由名单隔离，字节由共享承担。

**为什么播放必须纯只读。** 只要播放还会写，就永远存在「我明明没点下载，手机怎么少了 2 GB」的困惑——而这正是这次要消灭的东西。读写分离后，「占了多少空间」完全由用户的点击解释。

**为什么不做总量上限。** 空间不足是系统级问题，Android 自己会报警，用户会去清。给下载设上限意味着要么拒绝下载（体验差），要么按某个数字淘汰（又变回自动删）。删掉这个旋钮，少一块逻辑。

## 被否掉的方案

- **保留 5 GB 自动缓存 + 手动下载并存**：两个攒法叠在一起，用户分不清占了空间的是哪一类，界面要同时解释两套规则。否。
- **自定义 evictor 钉住手动下载、其余按 LRU 淘汰**：技术上可行（`applyContentMetadataMutations` 打标记 + 自写 ~60 行 evictor），但这等于把刚取消的自动缓存又留一半。
- **WorkManager / 前台服务跑下载**：见下面「后果」里的取舍——先不上，代价是可续传性。
- **下载时把列表状态记成就已下载（名单真相）**：离线时点进去放一半断掉，与「只有完整副本才算」的铁律正面冲突。否。
- **换账号时清掉上一个账号的下载**：等于每次换号毁掉几十 GB 的主动投入。否。

## 后果

- **`LeastRecentlyUsedCacheEvictor` / 5 GB 上限整段消失。** 手机空间从此完全由用户手动管理。这是有意的：设置页的「下载」卡片给出占用数字，是唯一的管理入口。
- **下载不保证完成。** 没有前台服务、没有 WorkManager，App 被系统杀掉下载就中断。重进 App 后按字节真相显示为「未下载」，用户再点一次即可（`CacheWriter` 会跳过已有部分）。这是刻意接受的简化——加 WorkManager 要引入「任务与会话绑定」的整套逻辑，跟「失败静默」的铁律要重新对齐。
- **串行下载。** 同时只跑一张专辑/一个列表，多张排队。跟 QQ 音乐导入服务的单工作线程一致，避免抢带宽影响播放（USB 独占下带宽被抢容易爆音）。
- **「清空缓存」这个操作整体消失。** 设置页只剩「下载」：占用 + 首数 + 进入管理列表。没有「一键清空全部」——那正是 `NoOpCacheEvictor` 要避免的东西，逐个专辑删是有意的摩擦。
- **`MediaCache` 这个接口名要改。** 它现在的语义变成「下载库」，不是「缓存」。实现仍包 `SimpleCache`，但对外词汇统一为「下载 / 已下载」（见 `CONTEXT.md`）。
- **QQ 音乐那个入口改名「QQ 音乐导入」**，把「下载」这个词让给手机上的这个功能。设置里两个含「下载」的卡片会让人认错。
- **播放列表需要一份「已下载列表」的本地清单**，否则「下载了整张歌单却离线看不到它」很奇怪。只存被下载过的那些，不是全量。
