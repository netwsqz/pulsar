# ADR-0009：删除流派页

**状态：** 已接受（2026-11-01）

**部分取代：** [ADR-0006](0006-unified-search-and-download-service-page.md) 决定 4 里的顶层列表（其余决定仍然成立）

## 背景

顶层导航此前有六个曲库维度：发现 / 歌曲 / 专辑 / 艺术家 / 流派 / 播放列表。

流派页与艺术家页是**同一套实现的第二个入口**：都由已加载的专辑在客户端分组（`libraryGroups`），
列表页和详情页只差一个分组维度参数。用下来发现：

- **流派几乎没人点。** 用户找音乐走歌手、专辑、播放列表，极少按流派翻。
- **流派数据本身不可靠。** Jellyfin 曲库里的流派标注稀疏、写法不统一（"Rock" / "rock" / "Rock/Pop"），
  分组结果的完整度取决于服务器元数据，和艺术家维度不是一个可信度。
- **多一个维度就多一整套维护面。** 列表空态、详情返回来源、导航索引导向都要为流派单独留分支，
  而它带来的价值远低于成本。
- **留下艺术家页没有损失。** 艺术家维度使用频率高、数据稳定，行为完全独立于流派页。

## 决定

**顶层导航删除「流派」，从 6 项收敛为 5 项：发现 / 歌曲 / 专辑 / 艺术家 / 播放列表。**

- 删除 `LibrarySection.Genres`；`LibrarySection.GroupDetail` 去掉 `isGenre`，只表示艺术家组。
- `libraryGroups` 收敛为艺术家-only；删除 `groupAlbumsByGenre`。
- 艺术家列表 / 详情去掉 `byGenre` / `isGenre` 分支，行为保持不变。
- 组详情的返回来源固定为艺术家页，不再靠 `isGenre` 反推。
- `navIndex()` 继续按 `TopLevelSections` 的位置推导，测试按类型 / 列表位置断言，不硬编码索引。

**保留数据字段：** `Album.genres`、DTO 的 `Genres` 字段与请求参数 `Fields=Genres` 原样不动。
它们属于数据层能力，将来若做服务端分组或其他维度还能用；删页面不等于删数据。

## 理由

- **一个维度要么有人用，要么不值得占顶层位置。** 顶层 chip 是最贵的界面资源，六个已经需要横向滑动。
- **同类实现只留一份。** 艺术家与流派共用 `libraryGroups` 时，每个改动都要在两种维度上各想一遍；
  收敛到一个维度后，列表 / 详情 / 空态 / 返回逻辑都只有一条路径。
- **数据层与界面层解耦。** 删除页面不碰 DTO 和请求参数，避免为了界面取舍去动网络契约。

## 后果

- `TopLevelSections` 少一项；chip 栏不再出现「流派」。
- `LibrarySectionTest` 的顶层顺序与 `navIndex` 断言改为按列表位置推导；`LibraryGroupsTest`
  删除流派分组用例，保留艺术家分组的既有边界（大小写不敏感、空白 / `UNKNOWN_ARTIST` 不建组、稳定排序）。
- ADR-0008 的离线范围列表同步注明流派页已删除。
- 界面不再有「暂无流派」空态；艺术家列表 / 详情路径不受影响。
